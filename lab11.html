Laboratorio de Path Traversal

File Path Traversal, Validation of Start of Path

Nivel: Practitioner | Tipo de explotación: Path Traversal / LFI

Detalles del Reporte

Objetivo del laboratorio

El objetivo de este laboratorio es explotar una vulnerabilidad de path traversal en la visualización de imágenes de productos . La aplicación transmite la ruta completa del archivo y valida que la ruta suministrada comience con la carpeta esperada; para resolverlo, debes evadir esta restricción lógica utilizando secuencias de salto después de la ruta base autorizada y lograr extraer con éxito el contenido del archivo crítico del sistema operativo, /etc/passwd .

Explicación técnica de la vulnerabilidad

La vulnerabilidad radica en una deficiencia en el control de acceso y en la validación de entradas de la aplicación . El sistema intenta asegurar la lectura de archivos verificando estrictamente que el parámetro de entrada comience con un directorio base específico (por ejemplo, /var/www/images/) . Sin embargo, el backend no sanitiza ni normaliza la ruta para eliminar las secuencias relativas de navegación (como ../) que se añaden posteriormente, permitiendo omitir el filtro inicial .

Procedimiento paso a paso

  1. El proceso inicia con la apertura de la aplicación Burp Suite y el uso de su navegador integrado para evitar conflictos con certificados de seguridad .
  2. En la sección Proxy > Intercept, se verifica que la función de intercepción se encuentre activada (Intercept is on) para pausar y capturar de manera temporal las peticiones HTTP .
  3. Una vez capturada la solicitud HTTP objetivo (GET /image?filename=/var/www/images/XX.jpg), se hace clic derecho sobre ella y se selecciona la opción Send to Repeater .
  4. Dentro de la herramienta Repeater, al intentar una ruta absoluta directa, el servidor responde con un error indicando que falta el parámetro o archivo, confirmando que se exige el prefijo autorizado .
  5. Finalmente, para evadir el control, se conserva el directorio base requerido y se le concatena la secuencia de salto de directorio básica, generando el payload final: /var/www/images/../../../etc/passwd .
  6. Al enviar la solicitud modificada, el servidor responde con el código HTTP/2 200 OK, exponiendo íntegramente el contenido del archivo /etc/passwd .

Explicación del payload

El payload utilizado consiste en una ruta mixta que combina la validación del prefijo requerido con secuencias relativas de salto de directorio: /var/www/images/../../../etc/passwd . Al evaluar la cadena, el filtro verifica que los primeros caracteres coincidan con el directorio permitido (/var/www/images/), aprobando la solicitud. No obstante, las secuencias ../ retroceden en el árbol de directorios a nivel de sistema operativo, revelando la información confidencial .

Mitigación recomendada

  • Validación de ruta canónica: Antes de validar si una ruta comienza con el directorio esperado, es fundamental "canonicalizar" (resolver) la ruta utilizando funciones del sistema (por ejemplo, realpath()) .
  • Uso de funciones de mapeo seguro (Basename): Utilizar funciones integradas como basename() para extraer únicamente el nombre del archivo solicitado .
  • Validación mediante listas blancas (Whitelisting): Restringir los valores permitidos en los parámetros de entrada a un conjunto estricto de nombres de archivos válidos .
