Laboratorio de Path Traversal

File path traversal, traversal sequences stripped with superfluous URL-decode

Nivel: Practitioner | Tipo de explotación: PATH TRAVERSAL

Detalles del Reporte

Objetivo del laboratorio

El objetivo de este laboratorio es explotar una vulnerabilidad de path traversal en la visualización de imágenes de productos donde la aplicación bloquea secuencias de escape comunes (como ../) y realiza una decodificación URL de la entrada; para resolverlo, debes evadir esta restricción lógica mediante el uso de una doble codificación URL y lograr extraer con éxito el contenido del archivo crítico del sistema operativo, /etc/passwd.

Explicación técnica de la vulnerabilidad

La vulnerabilidad radica en una deficiencia en el control de acceso y en la validación de entradas de la aplicación, la cual intenta mitigar el riesgo de path traversal decodificando la entrada y bloqueando únicamente las secuencias relativas de navegación (como ../). Al decodificar el payload una sola vez en la fase de inspección, no detecta el salto, pero posteriormente el backend lo procesa en su forma decodificada, lo que permite a un atacante acceder de manera ilegítima a recursos críticos del sistema operativo, tales como el archivo /etc/passwd.

Procedimiento paso a paso

  1. El proceso inicia con la apertura de la aplicación Burp Suite y el uso de su navegador integrado, el cual evita conflictos de configuración con certificados de seguridad.
  2. En la sección Proxy > Intercept, se verifica que la función de intercepción se encuentre activada (Intercept is on) para pausar y capturar de manera temporal las peticiones HTTP.
  3. Una vez capturada la solicitud HTTP objetivo (específicamente la petición GET /image?filename=), se hace clic derecho sobre ella para desplegar el menú contextual y se selecciona la opción Send to Repeater.
  4. Dentro de la herramienta Repeater, se intenta enviar primero una ruta absoluta y luego un salto de directorio básico, obteniendo en ambos casos "No such file", lo que indica que el sistema implementa una validación.
  5. Finalmente, para evadir los controles, se toma la secuencia de salto básica, se codifica en URL una primera vez, y este resultado se codifica una segunda vez para generar el payload final.
  6. Al enviar la solicitud con la carga útil doblemente codificada, el servidor la procesa correctamente y devuelve una respuesta con el código de estado HTTP/2 200 OK, exponiendo el contenido íntegro del archivo /etc/passwd.

Explicación del payload

El payload utilizado en este laboratorio consiste en una ruta de navegación relativa codificada doblemente en formato URL, específicamente: %2520%2520%252f%2520%2520%252f%2520%2520%252fetc/passwd. Esta estructura se introduce en el parámetro afectado y elude el filtro de la aplicación, ya que al decodificar %25 se obtiene un %, dejando el payload como %2e%2e%2f. Al no encontrar coincidencias exactas con la secuencia bloqueada, el filtro lo deja pasar.

Mitigación recomendada

  • Validación posterior a la decodificación: Asegurarse de que cualquier filtro de seguridad o verificación de listas negras se aplique después de que la entrada del usuario haya sido decodificada completamente (URL, Base64, etc.) hasta su representación final o canónica.
  • Uso de funciones de mapeo seguro (Basename): Utilizar funciones integradas en el lenguaje de programación (como basename() en PHP o equivalentes) que extraigan únicamente el nombre del archivo solicitado.
  • Validación mediante listas blancas (Whitelisting): Restringir los valores permitidos en los parámetros de entrada a un conjunto estricto de nombres de archivos válidos o identificadores predefinidos.
